# Календарь звонков


[![hexlet-check](https://github.com/SvetaZalyadnova/ai-for-developers-project-386/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/SvetaZalyadnova/ai-for-developers-project-386/actions)

Разработайте совместно с ИИ сервис для бронирования календаря

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers
Как это должно работать: https://files.hexlet.app/a/2ipc5m
Упрощенный аналог Cal.com для бронирования встреч. Позволяет владельцу календаря публиковать доступные типы встреч, а гостям — выбирать свободные слоты на 14 дней вперед и записываться на звонки без регистрации и личных кабинетов.

## 🚀 Основные возможности

* **Для владельца:**
  * Владелец календаря: Задан заранее в системе, имеет фиксированные часы работы (например, с 09:00 до 18:00, часовой пояс Europe/Moscow) и набор типов встреч (15, 30, 60 минут).
  * Типы встреч: Название, описание и фиксированная длительность.
  * Просмотр списка всех предстоящих встреч.
* **Для гостя:**
  * Просмотр доступных слотов на ближайшие 14 календарных дней (с учетом рабочих часов, часового пояса и уже занятого времени).
  * Быстрая запись на выбранный слот без авторизации.
  * Защита от пересечений: Система гарантирует, что одно и то же время нельзя занять дважды. Следующая встреча может начинаться строго в момент окончания предыдущей (race conditions).

## Стек

* **Бэкенд:** Java 17+, Spring Boot
* **Контракт API:** TypeSpec (генерация OpenAPI спецификации и клиентского SDK)
* **Хранение данных:** В памяти процесса (In-Memory). При перезапуске приложения все созданные бронирования сбрасываются.
* **Контейнеризация:** Docker (Multi-stage сборка)
* **Фронтенд:** React, TypeScript, Vite, сгенерированный клиентский SDK.

## ⚙️ Правила и ограничения бизнес-логики

1. **Окно записи:** Ровно 14 календарных дней, сдвигается с течением времени.
2. **Рабочее время:** Настраивается в конфигурации бэкенда (например, с 09:00 до 18:00 в часовом поясе UTC).
3. **Конфликты и пересечения:** Пересечение интервалов строго запрещено, включая частичное наложение разных типов встреч. Следующая встреча может начинаться в момент окончания предыдущей. Механизм синхронизации защищает от одновременных запросов на один и тот же слот.
4. **Хранение:** Приложение работает в памяти процесса (`In-Memory`). **Внимание:** при перезапуске сервера все созданные бронирования удаляются.

## 📦 API и Контракты (TypeSpec & OpenAPI)

Проект спроектирован по принципу *Contract-First*:

## Запуск через Docker

Из корня репозитория соберите образ и запустите приложение:

```bash
docker build -t booking-calendar .
docker run --rm -p 8080:8080 \
  -e OWNER_API_TOKEN="$(openssl rand -hex 32)" \
  -e PORT=8080 \
  booking-calendar
```

Откройте `http://localhost:8080/booking`. Главная страница доступна по `/`, страница владельца — по `/owner`. Для production задайте `OWNER_API_TOKEN` как секрет сервиса и передайте контейнеру порт через `PORT` (по умолчанию `8080`). Бронирования хранятся в памяти процесса и сбрасываются при каждом перезапуске или пересоздании контейнера.

## Деплой в Render

Публичный сервис: https://xekslet-booking-calendar.onrender.com

Сервис развёрнут в Render из этого репозитория с окружением Docker. Задайте секрет `OWNER_API_TOKEN` в настройках сервиса; Render передаёт приложению переменную `PORT`. Постоянное хранилище для бронирований не настроено, поэтому бронирования сбрасываются при перезапуске сервиса.

Для Claude Code скопируйте безопасный шаблон MCP-конфигурации и предоставьте ключ Render через переменную окружения, не добавляя его в репозиторий:

```bash
cp .mcp.json.example .mcp.json
export RENDER_API_KEY="..."
```

Перезапустите Claude Code после настройки. Файл `.mcp.json` и `.env` исключены из Git; шаблон `.mcp.json.example` не содержит секретов. Документация: [Render MCP Server](https://render.com/docs/mcp-server).

## Использование

### Быстрый сценарий: от типа встречи до записи в списке владельца

1. Запустите backend и frontend.
2. Откройте `/owner`, введите токен владельца из `OWNER_API_TOKEN` и войдите.
3. В форме `Добавить тип встречи` создайте тип: slug, название, описание, длительность.
4. После сохранения тип появится в блоке `Типы встреч` на странице владельца.
5. Откройте `/booking`, выберите этот тип, затем свободный слот в ближайшие 14 дней и нажмите `Забронировать`.
6. Вернитесь на `/owner`: в блоке `Предстоящие встречи` появится новая запись с временем, гостем и типом встречи.

Это короткий полный путь проверки, что сервер принимает данные и владельческий список обновляется после создания и записи.

### Проверки проекта

Установите Java 17 или новее и инструменты, указанные в `mise.toml`, затем запустите все проверки одной командой:

```bash
mise trust
mise install
mise run check
```

Команда проверяет генерацию и актуальность OpenAPI/SDK, линтинг, тесты и сборку фронтенда, выполняет backend verify и запускает браузерный сценарий Playwright с реальными frontend и backend. GitHub Actions настраивает Java 17 и запускает эту команду на каждый push.

### Релизы

Release Please использует встроенный `GITHUB_TOKEN`: отдельный токен и repository secret не нужны. Он создаёт единый release PR из `main`, обновляет корневой `CHANGELOG.md` и версию в `.release-please-manifest.json`, а после слияния публикует тег и GitHub Release. Conventional Commits (`feat:`, `fix:` и другие) используются для формирования заметок; frontend и backend не версионируются отдельно.

GitHub не запускает новые `push`/`pull_request` workflows в ответ на действия, выполненные с `GITHUB_TOKEN`. Поэтому workflow проверок не стартует автоматически на release PR; релизный PR нужно проверять отдельно либо настроить иной механизм запуска проверок.

### Проверка в браузере (локально или в Codespaces)

Запустите backend в первом терминале:
```bash
cd backend
export OWNER_API_TOKEN="$(openssl rand -hex 32)"
printf 'Токен для входа владельца: %s\n' "$OWNER_API_TOKEN"
mvn spring-boot:run
```

Во втором терминале запустите frontend:
```bash
cd frontend
npm install
npm run dev -- --host 0.0.0.0
```

Откройте в браузере `http://localhost:5173/booking`. В Codespaces откройте вкладку **Ports**, пробросьте порт `5173` и нажмите **Open in Browser**; в адресе добавьте `/booking`. Чтобы открыть страницу владельца, перейдите на `/owner` или выберите ссылку **Владелец** на главной, затем введите напечатанный backend токен. Vite перенаправляет запросы `/api` к backend, поэтому пробрасывать порт `8080` не нужно.

Страница владельца находится по адресу `/owner` (например, `http://localhost:5173/owner`). Войдите с токеном, который задан на backend в `OWNER_API_TOKEN`. Приложение не выдаёт токен и хранит его только в памяти текущей вкладки; после перезагрузки потребуется ввести его снова.

Для production-сборки frontend выполните `npm run build` из каталога `frontend`. Полный production-образ собирается командой `docker build -t booking-calendar .`. Бронирования хранятся в памяти backend и исчезают при его перезапуске.

Список типов встреч, доступность и создание бронирований загружаются с backend через сгенерированный SDK.

### Локальный запуск бэкенда

```bash
cd backend
mvn spring-boot:run
```

Бэкенд на Spring Boot предоставляет `GET http://localhost:8080/api/health`, публичное бронирование и закрытые маршруты владельца под `/api/v1/owner`. Для доступа к ним задайте переменную окружения `OWNER_API_TOKEN` на сервере; без неё запросы владельца отклоняются. Не добавляйте токен во frontend или репозиторий.

Владелец может читать список активных типов и предстоящих бронирований, создавать и редактировать типы встреч и архивировать их. Запросы к owner API требуют `Authorization: Bearer <OWNER_API_TOKEN>`.

Контракт и SDK генерируются командой `npm --prefix typespec run generate`. Она создаёт OpenAPI в `openapi/` и клиентский SDK в `frontend/src/api/`.
